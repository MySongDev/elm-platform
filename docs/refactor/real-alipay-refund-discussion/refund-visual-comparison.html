真实支付宝退款：现在长什么样，该长什么样

当前"同意退款"只改了一行数据库状态，钱其实没退。这份对照展示接入 alipay.trade.refund 之后，后端流程、订单状态、以及管理端 / 用户端界面会发生什么变化。

对照一 · 后端行为

同一个"同意退款"，两种截然不同的后果

左边是仓库里现在的真实代码，右边是接入支付宝后的目标形态。差别不在结构，而在中间那几行"真的调了支付宝没有"。

现在 · approveRefund()

钱没动 
async approveRefund(orderNo, operator) {
  const order = await findOrder(orderNo)
  assertRefundReviewAllowed(order)

  return prisma.$transaction(async tx => {
    // 只是把字段改成"已退款"
    await tx.paymentOrder.update({
      data: {
        refundStatus: 'APPROVED',
        refundedAt: new Date(),
      },
    })
    await tx.orderActionLog.create({ ... })
  })
}
全程没有一行调用支付宝。数据库写着"已退款"，用户支付宝账户余额纹丝不动。演示够用，真上线即是资损。

目标 · approveRefund()

原路退回 
async approveRefund(orderNo, operator) {
  const order = await findOrder(orderNo)
  assertRefundReviewAllowed(order)
  if (order.refundStatus === 'APPROVED') return  // 幂等

  // ① 先向支付宝发起真实退款(事务外)
  const r = await alipay.refund({
    outTradeNo: order.orderNo,
    refundAmount: order.payableAmount,
    outRequestNo: `${order.orderNo}_R1`,
  })
  if (r.code !== '10000') throw BadRequest(r.sub_msg)

  return prisma.$transaction(async tx => {
    await tx.paymentOrder.update({ data: {
      refundStatus: 'APPROVED', refundedAt: new Date(),
      refundTradeNo: r.trade_no,  // 新增流水
    }})
    await tx.orderActionLog.create({ ... })
  })
}
先调 alipay.trade.refund 真退钱，成功（code=10000）才落库，并存下支付宝退款流水号 trade_no。
对照二 · 调用时序

点击"同意"之后，发生的事

当前是一步到位（因为不出网），真实退款多了"出网退钱—等结果—按成败落库"这段，也正是所有复杂度的来源。

现在

1 步
  1. 1
    改数据库字段
    refundStatus → APPROVED，写日志，返回。约 10ms。

目标

4 步
  1. 1
    幂等前置检查
    已是 APPROVED？直接返回，绝不二次退款。
  2. 2
    调支付宝退款（出网）
    alipay.trade.refund，携带 out_request_no 幂等号。约 1–3s。
  3. 3
    按返回码分流
    10000 → 继续；否则记失败日志并抛错，状态不变。
  4. 4
    短事务落库
    成功后才写 APPROVED + 退款流水号，与现在同构。

为什么第 2 步要"出事务"

支付宝接口耗时几百毫秒到数秒。若把它裹进 $transaction，数据库连接和行锁会被网络等待占住，高并发下拖垮连接池。正确做法：网络调用在事务外，拿到成功结果后再开一个短事务落库。

对照五 · 改动范围

真实退款牵动的 6 个层面

不是加一个函数就完事。按依赖顺序排列，标注难度——第 1–5 层构成"能讲清、能演示"的闭环，第 6 层是生产级加分项。

层面要做什么难度为什么绕不开
AlipayService加 refund() / queryRefund()低照抄现有 queryTrade 模式
Prisma schema加退款流水 / 请求号 / 金额字段 + 迁移低对账、客服、幂等都要
幂等设计out_request_no + 状态前置判断中点两次不能退两次钱
失败处理失败不改状态、记日志、可重试中高资损场景，必须严谨
契约 + 前端错误类型 + 管理端 loading/成功/失败中前后端一致 + 体验
对账兜底定时用 queryRefund 核对"处理中"退款高异步/抖动的最终一致性（可后补）

状态机要不要加 REFUNDING 态

支付宝退款多数同步返回（fund_change=Y 即到账）。作品集可先按同步处理 REQUESTED → APPROVED，在注释里标注"生产需补 REFUNDING + 对账"——这与本项目状态机"拒绝过度设计"的一贯风格一致。

字段与返回码依据支付宝官方文档：统一收单交易退款 alipay.trade.refund · 退款响应参数。代码现状引自 order-workflow.service.ts / alipay.service.ts / schema.prisma。
