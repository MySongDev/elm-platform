# uni-user 微信支付接入计划书（分会话开发）

> 日期：2026-11-12。范围：`apps/uni-user`、支付所需后端与 API 契约。
> 状态：规划已落盘；已有少量未验证代码，**不是功能完成**。
> 执行入口：[HANDOFF.md](./HANDOFF.md)；操作步骤：[02-implementation.md](./02-implementation.md)。
> 本目录位于 `.gitignore` 放行的 `docs/refactor/`，可随代码提交；目前未提交。

## 1. 目标与范围

让微信小程序拥有真实支付代码链路：可信金额建单 → 微信预支付 → 原生收银台 → 后端查单/通知确认 → 更新订单与购物车。商户手续、真实密钥、生产配置与真机实付留待条件具备后验收。

另一目标同等重要：**用多个独立会话完成开发，避免一个会话反复加载全仓、历史对话和大量工具输出，造成上下文与费用膨胀。**

| 功能 | 实现位置 | 说明 |
|---|---|---|
| 后端查价与金额快照 | `apps/server/src/modules/order/` | 根据真实商家、菜品、SKU、数量计算，不收信任前端价格 |
| 建单幂等与渠道隔离 | Prisma `PaymentOrder`、订单/支付业务层 | 同一用户同一请求不重复建单；同一请求不同内容报冲突 |
| 微信身份与预支付 | `apps/server/src/modules/payment/wechat/` | 用一次性 code 换 openid，不替换原有短信/密码登录 |
| 通知、查单、到账更新 | 后端微信支付业务、订单工作流、`api/callbacks` | 验签、解密、身份金额核对、幂等与并发保护 |
| 原生付款与结果确认 | `apps/uni-user/src/platform/payment.ts`、`pkg-order/` | 首次付款、续付、取消、失败、结果未知统一处理 |
| 结算快照与精确清车 | `utils/payment.js`、`store-cart.js`、两条结算入口 | 只消费已付款订单的商品数量，不清后来新增的商品 |
| 接入与上线说明 | `docs/engineering/`、本目录 | 开关默认关闭；区分代码验收与真实实付验收 |

### 1.1 平台与范围边界

- uni-app 不是只能用微信支付；**本次目标是微信小程序内的原生微信支付**。H5 保留既有支付宝 WAP；App/其他小程序支付不在本次范围。
- 推荐直连商户 APIv3 + 微信支付公钥模式；不在本次做服务商模式、平台证书自动轮换、分账、钱包或对账系统。
- 推荐一单一商家：购物车跨商家勾选时提示分别结算。自动拆单/合单收款另开任务，不能把虚拟 `cart-checkout` 当真实商家收款。
- 本次不是退款接入。微信订单的退款申请可沿用申请流程，但在真实退款实现前必须阻止审批把它写成已退款；明确告知用户/管理员暂不能执行微信资金退款。
- 不顺带改 JWT 默认密钥、替换认证方式、升级 uni-app 版本、重构无关 HTTP 策略或部署基础设施。
- 同源代码注释不能机械解释成所有平台必须一致：共用业务规则需要查对 web-user；微信特有通道不强加给 H5。如必须改变 H5 的共享语义，登记影响并单独验证。

## 3. 设计约束与不变量

### 3.1 金额与订单

1. 新微信建单仅接受真实 `shopId` 与商品选择（itemId、skuId、qty）及请求 ID，用户身份来自 JWT；客户端不能指定收款金额或下单人。
2. 查数据库中的商家、SKU 和配送费；明确数量上限、重复项归并、商品属于本店、最低起送金额与当前可用状态。没有库存能力则不能宣称已实现库存扣减。
3. 以整数分运算，拒绝无效/负数/溢出；数据库 Decimal 只作为存储边界转换。先落可信金额快照，续付不因菜单变化重新给旧单改价。
4. 幂等键按用户隔离；唯一约束覆盖并发创建和响应丢失。相同键相同选择返回原单；相同键不同选择报 409，不静默复用别人的订单。
5. 新微信订单显式写 `paymentChannel='WECHAT'`。已有 null 行保留旧行为；**不自动把历史支付宝/占位订单转成微信订单**。旧订单不能续微信支付时提示重新结算。
6. 生成支付宝链接、支付宝查单/通知都不能修改微信订单。不能靠“当前只有一个渠道配置”判断渠道。

### 3.2 微信协议与到账

1. AppID、商户号、商户证书序列号、商户私钥、微信支付公钥 ID/公钥、APIv3 密钥各司其职，不能混用；所有秘密只放后端。
2. code → openid 不意味着微信账号登录；原 JWT 登录继续有效。openid 与本次小程序 AppID 配套，不把 session_key 返回前端。
3. 请求签名、响应验签、通知原始字节验签、AES-GCM 解密均需测试；按官方协议核对，不能以解密成功替代验签。
4. 查单/通知都核对订单号、AppID、商户号、币种、订单总金额与交易号；优惠后的 payer_total 不能代替订单 total 做一致性核对。
5. 只有可信的成功交易能把 PENDING 改为 PAID。状态更新与 PENDING_PAYMENT → AWAITING_ACCEPTANCE 在同一事务中完成，且有条件写入防止旧响应覆盖新状态。
6. 重复通知/查单幂等；并发通知、查单、接单不能把履约状态倒退。CLOSED 收到 SUCCESS 等异常冲突要明确暴露与处理，不静默丢弃已到账事实。
7. 客户端 success 只表示收银台调用结果，不作为资金到账证明；取消或失败也可能需查单确认，不能直接关本地单。
8. 缺配置返回清晰错误且不模拟成功；下单缺配置时不要产生新的无效支付订单。

### 3.3 购物车与恢复

- 在第一次网络建单前持久化 requestId；响应丢失后用同一 ID 找回原单，不自动生成新 ID。
- 结算快照绑定用户、requestId 和最终 orderNo，至少有商品身份与数量；不能只保存当前勾选项或 shopId。
- 确认 PAID 后消费当次快照的数量，并记录消费完成以防重复查询/重启再次扣车。新草稿不能覆盖旧未完成订单的快照。
- PENDING、取消、网络错误、结果未知保留恢复信息；PAID/CLOSED 按明确规则清理，退出账号不能混用别人的草稿。
- 轮询仅在结果页可见时运行，离页/隐藏停止；迟到响应不得重新注册定时器。失败支持手动查询，不无限高速重试。

## 4. 分会话路线

原五批被细化为七个会话：增加半成品收口 S0，拆开后端预支付与到账确认，并将购物车基础放到支付页面接入之前。

| 会话 | 工作目标 | 依赖与交付边界 |
|---|---|---|
| **S0** | 验收并收口当前半成品 | 只检查已有 8 个代码文件；协议单测与配置关闭验证；不能标记支付完成 |
| **S1** | 可信查价、幂等、渠道隔离 | 基于 S0；完成领域建单能力与资金基础测试，补 factory/摘要/DTO/必要退款阻断 |
| **S2** | 预支付业务与 HTTP 契约 | 基于 S1；code/openid、续付、Controller/DTO/模块注册；首次接通生成参数；冻结消费端契约 |
| **S3** | 查单、通知、原子到账 | 基于 S2；完成支付与履约一致性及并发/失败测试；后端闭环到此才完成 |
| **S4** | 单商家结算、订单快照与清车 | 基于 S2 契约和 S3 语义；修两条入口、草稿恢复与幂等消费，暂不改支付页样式 |
| **S5** | 小程序付款、续付、结果页 | 基于 S3/S4；接 uni.requestPayment、真实查询、轮询生命周期、错误提示和页面文案 |
| **S6** | 联合回归、文档和验收交接 | 基于 S1—S5；只整合和修本任务缺陷，不另启大型退款/合单功能 |
| **L1（后续）** | 资质、部署、真机实付上线 | 用户提供资质并授权配置/上线后才执行；不阻塞七个代码会话 |

每个会话的文件清单、操作步骤、最小验证见实施书对应章节。测试跟随本批实施，不延迟到 S6 才添加。

## 5. 会话与上下文控制规则

- **一会话只做一个编号。** 达到该编号验收条件即更新 HANDOFF 并结束，不因“还剩时间”自动开始下一批。
- 默认串行、单会话开发，不自动创建工作流或多个子代理；用户另行要求时才调整。分会话不是同时多人修改同一分支。
- 新会话启动只读 HANDOFF、计划书第 1/3/5 节、实施书当前编号。政策文件按项目要求读；源码只读当前批清单及确实需要的直接依赖。
- 优先 Grep 找位置，再 Read 行段。不要全读迁移总方案、历史报告、coverage、dist、生成的长类型文件；生成物只核对相关 schema/operation。
- 通常先读 3—6 个相关源码文件；需要扩到约 10—12 个或遇到第二个独立问题时，先判断是否应拆成子会话，而不是扩大调研。文件数是成本提醒，不是禁止必要检查。
- 同一失败最多尝试两个有根据的修正方向；之后记录错误、定位和下一步，暂停本批，不重复跑相同失败命令。
- 日志只保留命令、退出码、测试数、关键错误；完整日志可本地保存，交接不复制全部输出。每批结尾约 10—20 行摘要即可。
- 全量回归原则上留 S6；各批跑相关测试和构建。资金不变量、现有测试失败和必要契约验证不得为了省费用跳过。
- 若剩余上下文不足以安全完成测试和交接，先停在可恢复点，状态写“部分完成”，下一会话仍完成同一编号，不假装已验收。

## 6. 阶段验收与完成口径

| 功能 | 实现位置 | 说明 |
|---|---|---|
| 代码完成 | 各批源码、测试、契约 | 必须完成本批范围且真实通过对应检查；文件存在不等于实现完成 |
| 数据库验证 | 本地/一次性测试数据库 | Prisma generate/validate 不等于迁移已执行；环境阻塞时明确记录，不能声称数据库通过 |
| 小程序编译验证 | `apps/uni-user` 构建产物 | type-check 与 build 分开执行；构建通过不等于微信运行时通过 |
| 无凭证测试验证 | Jest/Vitest 与本地假传输 | 使用本地测试密钥和替身，不调用真实收款、不提供伪造成功 API |
| 真机支付验收 | 微信开发者工具/真机/商户平台 | 需真实 AppID、绑定、凭证、HTTPS、合法域名；目前未执行 |

整体代码完成要求：S0—S6 均有验收记录、实际命令与剩余项；上线完成还要求 L1。没有商户资质时最终表述应为“接入代码完成，真实支付待联调”，不能写“已支持线上收款”。

## 7. 变更、授权与风险

- 当前分支继续使用，禁止新会话重新从 main 开分支丢掉已有改动；每批开头核对 HEAD 和工作区。
- 编码可按用户开发指令执行；commit、push、PR、merge、tag、真实支付、生产配置/迁移都需相应明确授权，不把上一批授权泛化到下一批。
- 不提交/清理其他任务的修改。不 reset/clean/stash 当前半成品。若无提交授权，以未提交清单和 HANDOFF 接力，同一目录不要并行开发。
- 本地开发迁移只能对已确认的开发/测试数据库执行；环境变量可能指向远端，不凭名字猜。生产迁移需另行授权。
- 收款技术不等于多商家资金合规方案；本次不提供自动分账，也不宣称已具备平台商家结算能力。
- 退款审批阻断是安全边界，真实退款是单独任务；上线前须有明确的客服/退款处理安排。

## 8. 官方依据（定点阅读）

仅在协议实现/审查时阅读需要的页面，不在每个会话重做网络调查。

- [小程序支付开发流程](https://pay.weixin.qq.com/doc/v3/merchant/4012791911.md)：收银台回调后应查询订单，不把前端结果当资金真相。
- [小程序调起支付](https://pay.weixin.qq.com/doc/v3/merchant/4012791898.md)：timeStamp、nonceStr、package、signType、paySign 的标准字段；真实 AppID 必须一致。
- [证书与密钥概览](https://pay.weixin.qq.com/doc/v3/merchant/4024350132.md)：商户私钥、公钥与 APIv3 密钥用途不同。
- [公钥模式注意事项](https://pay.weixin.qq.com/doc/v3/merchant/4054257713.md)：通知先验签再解密，验签失败不能当正常通知处理。

上述链接在 2026-11-12 已通过官方域名搜索核对；正式实施仍需补看对应下单、查单和通知接口文档，尤其错误响应/通知应答规则，不把本计划当第三方协议的全部规范。
