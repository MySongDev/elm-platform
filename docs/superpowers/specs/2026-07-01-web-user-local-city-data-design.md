# Web User 本地城市数据接入设计

## 1. 背景

`apps/web-user` 的 Home 页面需要展示城市列表。城市原始数据来自：

`https://cube.elemecdn.com/0ab56e557c67533275767af1fda3629e.json`

该资源约 236 KiB，包含 2252 条记录，单条记录结构如下：

```json
{
  "i": 1916,
  "n": "阿坝县",
  "p": "aba",
  "x": 32.904223,
  "y": 101.700985
}
```

运行时直接访问该 CDN 虽然具备跨域条件，但会让核心城市列表依赖第三方服务。目标是将数据作为本站静态资源管理，使生产运行时不再访问饿了么 CDN。站点的其他功能仍按现有方式联网运行，本次不引入 PWA 或整站离线能力。

## 2. 已确认需求

- 城市数据必须由本站提供，运行时不得依赖外部 CDN。
- Home 页面首版一次性展示全部 2252 条记录。
- 原始 JSON 数组的前 9 条记录作为热门城市；不按 `i` 数值重新排序。
- 保持现有城市点击、位置写入和路由跳转行为。
- 保留可重复执行的人工更新流程，但更新动作不在生产运行时发生。
- 本次不增加后端城市接口、数据库表、PWA 或虚拟列表。

## 3. 方案比较

### 3.1 推荐：本站原始 JSON + 同源异步加载

将紧凑的原始 JSON 保存到 `apps/web-user/public/data/china-cities.json`。前端通过带 `BASE_URL` 的同源地址加载，并在数据层完成校验、字段标准化、热门城市截取和字母分组。

优点：

- 完全解除生产运行时对饿了么 CDN 的依赖。
- JSON 独立于 JavaScript 包，可单独缓存。
- 保留原始紧凑字段，避免生成冗长 TypeScript 对象导致源码和构建产物膨胀。
- 更新数据时只需重新下载并校验静态文件。

代价：

- 首次进入 Home 时会产生一次本站静态资源请求。
- 页面需要明确处理加载、失败和重试状态。

### 3.2 TypeScript 数据常量

把 2252 条数据展开为 TypeScript 对象并直接导入。该方案已在当前仓库的最新提交中出现，但生成文件约 514 KiB，并会进入 JavaScript 模块的下载、解析和执行流程。它具备类型提示，但不适合这类体积较大的静态数据。

### 3.3 后端 API

由 NestJS 读取文件或数据库并返回城市数据。该方案便于集中治理，但增加服务端实现、部署和可用性依赖；对于当前稳定、只读的数据集没有足够收益。

## 4. 架构与职责

### 4.1 静态数据文件

`apps/web-user/public/data/china-cities.json`

- 保存从指定 CDN 下载的原始 JSON 数组。
- 保留 `i`、`n`、`p`、`x`、`y` 字段，不在文件中复制派生字段。
- 与应用代码一起部署，由本站静态资源服务提供。

### 4.2 城市数据加载模块

新增一个专用城市数据模块，职责包括：

- 使用 `${import.meta.env.BASE_URL}data/china-cities.json` 构造部署安全的 URL。
- 检查 HTTP 状态和顶层数组结构。
- 校验每条记录的字段类型与有限数值。
- 将原始字段标准化为现有页面使用的模型。
- 用模块级 Promise 复用同一次加载与解析结果。
- 在失败后清除失败的 Promise，使用户重试能够重新发起请求。

标准化映射：

| 原始字段 | 页面字段 |
| --- | --- |
| `i` | `id` |
| `n` | `name` |
| `p` | `pinyin` |
| `x` | `latitude` |
| `y` | `longitude` |

`geohash` 不在静态数据中重复保存。若现有路由仍需要该值，则在标准化阶段沿用项目当前的坐标字符串约定生成，避免改变现有导航契约。

### 4.3 API 兼容层

`apps/web-user/src/services/api/api-city.js` 保留现有公开函数：

- `getHotCity()`：从标准化结果中返回原始顺序的前 9 条。
- `getGroupCity()`：按 `pinyin` 首字母生成 A–Z 分组。

两个函数共享城市数据加载模块，不重复请求或解析 JSON。其他仍由后端提供的定位、逆地理编码和地点搜索接口保持不变。

### 4.4 响应式数据层

`apps/web-user/src/composables/swr/useSWRCities.ts` 不再静态导入大型 TypeScript 数据文件，而是调用兼容 API。它继续向页面暴露响应式数据，并利用现有 SWR 机制处理生命周期。

若现有 SWR 接口不能表达显式重试，则在不改变通用 SWR 行为的前提下，为 Home 提供最小的城市加载封装；不为本功能引入新的全局状态管理。

### 4.5 Home 页面

`apps/web-user/src/views/home/home.vue` 只负责：

- 展示当前定位。
- 展示 9 个热门城市。
- 按字母分组一次性展示全部城市。
- 展示城市数据的加载、失败、空数据和重试状态。
- 在用户选择城市后沿用现有位置写入与路由跳转逻辑。

Home 不直接读取原始 `i/n/p/x/y` 字段，也不负责数据分组。

## 5. 数据流

```text
本站 /data/china-cities.json
        |
        v
城市数据加载模块（请求、校验、标准化、单例缓存）
        |
        +--> getHotCity()   --> 原始顺序前 9 条
        |
        +--> getGroupCity() --> 按拼音首字母分组的全部数据
                                |
                                v
                             Home 展示
```

## 6. 状态与错误处理

- `loading`：Home 显示与现有视觉风格一致的加载提示。
- `success`：同时呈现热门城市和全量分组。
- `empty`：数据数组为空时显示明确的空数据提示，不渲染空分组。
- `error`：HTTP 失败、JSON 解析失败或数据结构不合法时显示错误提示和重试入口。
- `retry`：清除本次失败状态并重新加载本站 JSON。

不得静默回退到饿了么 CDN，否则会破坏“不依赖外部 CDN”的核心约束。

## 7. 数据更新流程

保留一个仅供开发者手动执行的生成脚本：

1. 从固定 CDN 地址下载 JSON。
2. 验证 HTTP 成功、记录数量、字段类型和 `i` 唯一性。
3. 使用稳定 JSON 序列化写入站内静态文件。
4. 输出记录数量、文件大小和校验摘要。
5. 由代码评审确认数据文件变更后随应用发布。

该脚本不得在 `dev`、`build` 或生产启动流程中自动运行，以保证构建可复现且不受外网可用性影响。

## 8. 测试与验收

### 8.1 单元测试

- 正确映射 `i/n/p/x/y` 字段。
- 拒绝非数组、字段缺失、字段类型错误和非法坐标。
- 校验 `id` 唯一性。
- `getHotCity()` 严格返回原始数组前 9 条。
- `getGroupCity()` 按拼音首字母分组且不丢失记录。
- 并发调用只触发一次加载和解析。
- 首次失败后允许重试并成功。
- 静态数据文件包含预期的 2252 条记录。

### 8.2 页面验收

- Home 显示 9 个热门城市。
- Home 按 A–Z 分组一次性显示全部 2252 条记录。
- 点击热门城市或普通城市后，位置坐标、城市名称和城市 ID 正确写入。
- 路由跳转行为与改造前一致。
- 加载失败时页面可见错误提示和重试入口。
- 浏览器网络面板中不存在对 `cube.elemecdn.com` 的运行时请求。

### 8.3 工程验证

- 运行城市数据相关单元测试。
- 运行 `apps/web-user` 类型检查。
- 运行 `apps/web-user` 构建。
- 检查构建产物中城市 JSON 由本站提供，且大型 TypeScript 城市常量不再进入 JavaScript 包。

## 9. 性能边界

本次按产品决定一次性渲染全部 2252 条记录。该行为可能在低端移动设备上造成较长的 DOM 创建时间和滚动压力，但性能优化不属于本次首版范围。

实现完成后记录实际页面表现。如果出现可感知卡顿，后续独立设计搜索、折叠分组、分批渲染或虚拟列表，不在本次实现中提前引入这些复杂度。

## 10. 非目标

- 不实现整站断网可用。
- 不引入 Service Worker 或 PWA。
- 不定时从第三方 CDN 自动同步。
- 不修改 NestJS 城市服务或数据库。
- 不改变定位、逆地理编码和地点搜索的数据来源。
- 不在本次实现中加入城市搜索、折叠分组或虚拟滚动。
